# 高校官网发现与公告情报管线方案（2026-03-18）

本文档将“输入学校/学院名称，自动定位官网，发现更新公告，筛选研招相关内容，清洗并展示”的想法整理为可执行方案。

## 1. 产品目标

用户输入：

- 学校名称
- 下属学院名称（可选）

系统完成：

1. 找到学校官网、研究生院官网、学院官网及其公告栏目页。
2. 监控这些页面是否有新公告或更新。
3. 抓取新增公告，支持 HTML、PDF，后续可扩展 OCR。
4. 使用固定关键词和自定义关键词筛选与通知公告、研招信息、调剂、复试等相关的内容。
5. 清洗正文，提取结构化字段。
6. 以网站可直接阅读和检索的形式展示，并保留原始链接与原始快照。

## 2. 不建议的做法

以下方案看起来省事，但长期会拖垮可维护性：

- 每次查询都临时调用搜索引擎再抓取结果页
- 只保存清洗后的结果，不保存原始 HTML / PDF
- 把 PDF 当特殊情况临时处理
- 只做全文爬取，不做结构化字段提取
- 不做去重，只靠标题模糊判断是否更新

## 3. 推荐总体架构

建议拆成五层：

### 3.1 站点资产层

作用：沉淀“学校 -> 学院 -> 官网 -> 栏目页”的长期资产，而不是每次都临时搜索。

建议维护：

- 学校主站
- 研究生院站点
- 学院站点
- 栏目页
  - 通知公告
  - 研究生招生
  - 调剂相关
  - 招生简章
  - 复试录取

搜索引擎适合：

- 初始化建库
- 站点缺失时辅助发现
- 官网迁移后的补链

搜索引擎不适合：

- 高频实时生产依赖

### 3.2 更新发现层

作用：判断某个栏目页是否出现新内容。

推荐方式：

- 先抓列表页
- 从列表页发现新增详情链接
- 再抓详情页正文

更新判断依据：

- `source_url` 新增
- 标题变化
- 发布时间变化
- 内容哈希变化

### 3.3 内容抓取层

输入：

- HTML 详情页
- PDF 附件
- 附件下载页

建议输出四份材料：

- 原始 HTML
- 原始 PDF / 文件
- 提取后的纯文本
- 结构化清洗结果

### 3.4 内容理解层

目标不是只拿正文，而是抽取结构化信息。

建议抽取字段：

- 学校
- 学院
- 公告标题
- 公告类别
- 发布时间
- 原始链接
- 正文摘要
- 命中关键词
- 专业
- 方向 / 学科
- 调剂 / 复试 / 招生简章 / 录取等标签
- 报名时间 / 截止时间
- 联系方式
- 附件信息

### 3.5 展示与订阅层

用户最终看到的不是一坨原文，而应该是：

- 情报卡片
- 清洗后的正文
- 结构化信息块
- 原始来源链接
- 附件入口
- 关键词命中说明

`Markdown` 可以作为中间归档格式，但前台展示建议仍以结构化渲染为主。

## 4. 固定关键词与自定义关键词

建议把筛选分两层：

### 4.1 固定关键词库

由系统内置，用于判定是否与研招相关。

示例：

- 通知公告
- 研究生招生
- 招生简章
- 调剂
- 复试
- 拟录取
- 推免
- 录取名单
- 报名通知
- 硕士招生
- 博士招生

### 4.2 自定义关键词库

由用户或管理员维护，用于个性化命中。

示例：

- 学院名
- 专业代码
- 导师方向
- 学科关键词
- 某地区 / 某项目名称

### 4.3 筛选策略

建议输出三层相关性：

- `high`：强相关，直接进入主结果流
- `medium`：可疑相关，进入人工复核或次级结果
- `low`：弱相关，只留痕，不对外展示

## 5. HTML 与 PDF 处理策略

### 5.1 HTML

优先抽取：

- 标题
- 发布时间
- 正文节点
- 附件链接

保留：

- `raw_html`
- `raw_text`
- `snapshot_meta`

### 5.2 PDF

必须视为一等公民，不建议后补。

建议支持三类：

- 文本型 PDF：直接提取文本
- 扫描型 PDF：记录 OCR 待处理状态
- HTML + PDF 混合公告：HTML 为摘要，PDF 为正文细则，二者做关联

建议记录：

- 文件 URL
- 文件类型
- 提取状态
- OCR 状态
- 提取文本长度
- 解析失败信息

## 6. 推荐数据模型扩展

当前仓库已有：

- `schools`
- `sources`
- `contents`
- `content_snapshots`
- `crawl_jobs`
- `crawl_errors`

建议下一步扩展以下模型：

### 6.1 `departments`

作用：

- 维护学院/研究生院实体
- 建立与学校的归属关系

建议字段：

- `id`
- `school_id`
- `name`
- `aliases`
- `department_type`
- `enabled`

### 6.2 `site_sections`

作用：

- 表示具体栏目页

示例：

- 某大学研究生院通知公告页
- 某学院招生信息页

建议字段：

- `id`
- `school_id`
- `department_id`
- `source_id`
- `name`
- `section_type`
- `section_url`
- `list_selector_config`
- `detail_selector_config`
- `enabled`

### 6.3 `content_files`

作用：

- 统一管理 PDF、附件、图片型公告

建议字段：

- `id`
- `content_id`
- `file_url`
- `file_type`
- `mime_type`
- `text_extracted`
- `parse_status`
- `ocr_status`
- `file_meta`

### 6.4 `keyword_rules`

作用：

- 固定词库与自定义词库统一管理

建议字段：

- `id`
- `scope`
- `rule_type`
- `keyword`
- `weight`
- `enabled`

### 6.5 `content_matches`

作用：

- 保存某条内容命中了哪些规则，便于解释性展示和审计

建议字段：

- `id`
- `content_id`
- `rule_id`
- `matched_text`
- `score`
- `created_at`

## 7. 采集流程建议

推荐按以下链路实现：

1. 管理员录入学校 / 学院 / 官网 / 栏目页。
2. 系统定期扫描 `site_sections`。
3. 列表页发现新增链接，生成抓取任务。
4. 抓取详情页：
   - HTML 正文
   - 附件 URL
   - PDF 文件
5. 原始内容入库：
   - `contents`
   - `content_snapshots`
   - `content_files`
6. 运行关键词筛选与结构化提取。
7. 生成对外可展示结果。
8. 命中订阅规则时触发通知链路。

## 8. MVP 范围建议

不建议第一阶段就做“全国所有高校 + 全自动站点发现”。

更稳的 MVP 方案：

### 阶段 1

- 只选 `10~20` 所学校
- 每校只盯：
  - 研究生院
  - 目标学院
  - 通知公告页
  - 研招页
- 只支持：
  - HTML
  - 文本型 PDF
- 关键词以规则库为主，不急着上复杂 NLP

### 阶段 2

- 扩大学校覆盖面
- 接扫描型 PDF/OCR
- 增加栏目自动发现与补链
- 增加相关性评分和人工复核面板

### 阶段 3

- 增加更多结构化抽取能力
- 增加多通道通知
- 增加对外搜索、收藏、订阅能力

## 9. 对现有项目的最合理落地方式

结合你当前仓库，最适合的做法不是立刻推翻，而是在现有 Task Pack A 基础上继续演进：

### 第一步

先把 `crawl_jobs` 跑稳，让它支持：

- 列表页抓取
- 详情页抓取
- 快照留存
- 失败留痕

### 第二步

在 `sources` 之上补：

- `departments`
- `site_sections`
- `content_files`

### 第三步

补关键词规则和命中解释：

- `keyword_rules`
- `content_matches`

### 第四步

前台增加“清洗后的公告阅读页”和“命中说明”

## 10. 推荐下一步任务

如果要继续推进，最建议的下一个实现包是：

1. `Task Pack A-2`
   - 在现有最小抓取任务流上增加 `site_sections` 驱动的列表页发现
2. `Task Pack A-3`
   - 增加 `content_files`，接通 PDF
3. `Task Pack A-4`
   - 增加固定关键词规则和内容命中记录

## 11. 当前实现快照（2026-03-18）

已落地（最小版）：

- `departments` / `site_sections` / `site_section_links` / `content_files` 数据结构已接入。
- `site_sections` 管理接口已可用（创建、列表、按筛选触发 discovery、查看 links）。
- crawler worker 已支持 `site_section_discovery`：
  - 列表页发现新 HTML 链接并生成后续详情抓取任务；
  - 识别 PDF 链接并写 `content_files` 占位记录；
  - 失败回写 `crawl_errors` 与 section 状态。

尚未落地（后续阶段）：

- 精细选择器驱动的列表抽取（当前仍以通用 `<a>` 链接发现为主）。
- PDF 正文抽取/OCR。
- 跨栏目/跨站点全局去重与公告聚合。
- 关键词规则命中与解释链路（`keyword_rules` / `content_matches`）。
- 真正意义上的“只给学校名，系统自己全网找官网”的外部搜索冷启动。

新增（2026-03-23）：

- `POST /api/v1/site-sections/bootstrap` 已可用：
  - 输入 `school_name + homepage_url`，系统会在同 host 下自动探测研究生院/研招/通知/调剂类栏目链接；
  - 自动创建 `sources` / `site_sections` 资产；
  - 可选立即排 `site_section_discovery` 任务。

## 12. 一句话总结

这个功能最好的产品形态，不是“通用爬虫”，而是：

一个围绕高校研招场景、具备官网发现、更新监控、HTML/PDF 抽取、关键词筛选、结构化整理和订阅通知的情报系统。
