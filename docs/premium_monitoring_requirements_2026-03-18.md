# 高级院校公告监控功能需求（2026-03-18）

本文档用于定义“由高级用户自定义选择学校/学院监控目标，并按关键词监控新公告后推送”的完整实现要求。

## 1. 功能定位

这不是一个固定学校白名单功能，而是一个：

- 可扩展的院校/学院公告监控器
- 面向高级用户的付费/高阶能力
- 管理员默认拥有全部能力

系统目标：

1. 用户可自定义选择学校、研究生院、学院、栏目页作为监控对象。
2. 系统按配置频率自动检查是否有新公告。
3. 对新增公告执行关键词筛选。
4. 命中结果推送给当前用户，并在网站中可直接查看。

## 1.1 Phase 1 实施状态注记（Implemented / Planned）

本节用于区分“已实现”与“规划中”，避免把需求描述误读为全部已上线。

Implemented（截至 2026-03-18 已在主干相关工作中可见）：

- `departments / site_sections / site_section_links / content_files` 的最小站点资产与列表发现链路。
- `crawl_jobs / contents / content_snapshots / crawl_errors` 的抓取闭环与失败留痕。
- 站内通知基座（`notification_outbox / notification_deliveries`）与 Bark 最小通道能力。
- `portal_user_monitor_targets / portal_user_monitor_keywords / portal_user_monitor_hits` 三张监控核心表已接入后端模型。
- `/api/v1/monitoring/*` 的目标配置、关键词配置、命中查询、管理员命中查询接口已接入。
- 内容入库后会执行一次用户级命中计算，并写入 `monitor.hit` outbox 事件。

Planned（Phase 1 目标但在部分分支仍待接线）：

- 管理员“开通/关闭 premium 资格”的显式后台接口与操作流。
- 监控目标重复约束在不同数据库引擎上的一致性治理。
- 管理员后台监控命中数据面板与更细粒度筛选。
- 复杂匹配能力（regex、分层评分、排序增强）与 PDF 深度解析能力。

## 2. 用户与权限模型

基于当前仓库，建议按以下关系实现：

### 2.1 `User`

当前含义：

- 微信侧 `shadow` 访客用户
- 用于小程序静默登录和访问审计

建议：

- 当前不要把“高级监控器”直接挂在 `User` 上
- 保持它作为轻量匿名/影子身份
- 未来若小程序也要使用高级监控，再增加与 `PortalUser` 的绑定关系

### 2.2 `PortalUser`

当前含义：

- 网站正式注册用户
- 拥有登录、会话、订阅、Bark 等能力

建议：

- 高级监控功能的核心拥有者应为 `PortalUser`
- 所有监控目标、关键词规则、推送偏好，都挂在 `PortalUser` 维度

### 2.3 `AdminAccount`

当前含义：

- `PortalUser` 的 1:1 管理员扩展表

建议：

- `AdminAccount` 用户自动拥有全部高级监控权限
- 管理员不受普通用户配额限制
- 管理员可查看后台监控数据、任务状态、监控命中结果和运行健康状态

## 3. 权限要求

### 普通用户

- 只能使用基础功能
- 不能创建高级院校监控目标
- 不能查看后台监控数据

### 高级用户

- 可创建/编辑/停用自己的监控目标
- 可设置自定义关键词
- 可查看自己的命中结果与推送记录
- 可订阅学校级、学院级、栏目级监控

### 管理员

- 默认拥有全部高级监控权限
- 可查看所有用户相关监控数据
- 可查看和维护站点资产
- 可查看 crawler 状态、错误记录、命中数据、推送结果

## 4. 核心业务对象

### 4.1 站点资产

站点资产由系统维护，供监控功能复用。

建议对象：

- `schools`
- `departments`
- `sources`
- `site_sections`

说明：

- `school` 表示学校
- `department` 表示研究生院/学院
- `site_section` 表示可监控栏目页

### 4.2 用户监控目标

这是高级功能的核心对象。

建议新增：

- `portal_user_monitor_targets`

建议字段：

- `id`
- `user_id`
- `school_id`
- `department_id` 可空
- `site_section_id` 可空
- `scope_type`
  - `school`
  - `department`
  - `section`
- `status`
  - `active`
  - `paused`
  - `deleted`
- `check_interval_minutes`
- `last_checked_at`
- `last_hit_at`
- `created_at`
- `updated_at`

设计原则：

- 支持用户按学校监控
- 支持按学院监控
- 支持按具体栏目页监控

### 4.3 用户关键词规则

建议新增：

- `portal_user_monitor_keywords`

建议字段：

- `id`
- `user_id`
- `monitor_target_id`
- `keyword`
- `match_mode`
  - `contains`
  - `regex`（后续）
- `weight`
- `status`
- `created_at`

说明：

- 固定关键词规则与用户自定义关键词规则分开管理
- 用户关键词应挂在监控目标下，避免全局污染

### 4.4 监控命中记录

建议新增：

- `portal_user_monitor_hits`

建议字段：

- `id`
- `user_id`
- `monitor_target_id`
- `content_id`
- `site_section_id`
- `matched_keywords`
- `match_score`
- `hit_reason`
- `pushed_inapp`
- `pushed_bark`
- `created_at`

说明：

- 这是“公告命中了哪个用户的哪些规则”的结果表
- 便于展示、去重、通知和后台分析

## 5. 监控流程要求

### 5.1 目标配置

高级用户在网站中：

1. 搜索学校或学院
2. 选择监控范围
   - 学校级
   - 学院级
   - 栏目级
3. 设定检查频率
4. 添加自定义关键词
5. 保存监控目标

管理员可以：

- 直接创建和维护这些目标
- 查看所有用户目标

### 5.2 定时监控

系统根据监控目标定时生成抓取任务。

建议频率分层：

- 高频栏目：30~60 分钟
- 中频栏目：2~4 小时
- 低频栏目：12~24 小时

不要默认所有目标都一样频率。

### 5.3 更新发现

对指定 `site_section` 扫描列表页：

- 发现新的详情链接
- 生成详情抓取任务
- 记录来源 section

### 5.4 内容抓取

抓取结果支持：

- HTML 正文
- PDF 附件
- 附件链接留痕

必须保留：

- 原始链接
- 原始快照
- 失败留痕

### 5.5 关键词筛选

筛选基于两层规则：

- 固定词库
- 用户自定义词

结果分层：

- `high`
- `medium`
- `low`

至少要求：

- 命中记录可解释
- 能展示命中了哪些词

### 5.6 推送与展示

命中后：

- 写入用户命中记录
- 触发站内通知
- 如用户开启 Bark，则可推 Bark

网站中要支持：

- 监控目标列表
- 命中结果列表
- 公告详情页
- 命中关键词展示

## 6. 后台要求

管理员后台至少应能看到：

- 当前监控目标总数
- 按学校/学院/栏目页的监控分布
- 各监控目标最近检查时间
- crawler 任务状态
- `crawl_errors`
- 命中结果数量
- 推送成功/失败情况

建议后台支持：

- 按用户筛选
- 按学校筛选
- 按学院筛选
- 按栏目页筛选
- 按命中关键词筛选

## 7. 非功能要求

### 7.1 可扩展性

- 学校和学院绝不能写死在代码逻辑里
- 首批样本只是 seed 数据和验收样本
- 必须支持后续继续新增任意学校/学院/栏目页

### 7.2 可追踪性

- 任务要可追踪
- 错误要可追踪
- 命中要可追踪
- 推送要可追踪

### 7.3 去重

至少需要处理：

- 同一栏目重复抓取
- 同一用户对同一内容重复命中
- 同一内容多次重复推送

### 7.4 性能与频率控制

- 不要为每个用户单独爬一次
- 正确做法是：
  - 系统抓一次内容
  - 多个用户在内容结果上做命中匹配

这是实现成本和性能成本的关键。

## 8. 分阶段实现建议

### 阶段 1：最小可运行高级监控器

实现：

- `departments`
- `site_sections`
- `portal_user_monitor_targets`
- `portal_user_monitor_keywords`
- `portal_user_monitor_hits`
- 用户目标配置 API
- 定时/准定时检查目标 section
- 基础命中与站内通知

### 阶段 2：增强推送与后台可视化

实现：

- Bark 结合命中结果推送
- 后台监控数据面板
- 更细粒度筛选
- 用户配额与套餐限制

### 阶段 3：更强内容理解

实现：

- PDF 文本抽取增强
- OCR
- 更强关键词和结构化提取
- 相关性评分优化

## 9. 关键实现约束

`3codex` 实现时必须遵守：

- 不要把学校/学院写死在代码里
- 不要把“用户监控目标”和“站点资产”混成一张表
- 不要为每个用户重复抓相同网站
- 不要把管理员特权做成单独平行体系，优先复用 `PortalUser + AdminAccount`
- 不要跳过 docs、测试、部署验证

## 10. 一句话定义

这个功能的正式定义应为：

高级用户可自定义选择学校、研究生院、学院或栏目页作为监控目标，系统按配置频率自动检查新公告，并将命中固定关键词与自定义关键词的内容清洗后展示并推送给该用户；管理员默认拥有全部能力并可查看后台监控数据。
