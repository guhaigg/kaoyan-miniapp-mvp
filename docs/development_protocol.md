# 格物简录 Development Protocol

本文件是项目统一执行规范。目标是让任何后续接手者都能按同一标准稳定开发、测试、提交和发布。

## 1) 适用范围

- 适用于本仓库全部开发工作：小程序、后端、部署、文档。
- 适用于日常迭代、缺陷修复、线上变更和紧急修复。

## 2) 开发前必做

1. 先读并遵守：
   - `docs/plan.md`
   - `docs/git_workflow.md`
   - `docs/deployment.md`
2. 检查当前分支和工作区状态，避免在脏状态下误操作。
3. 涉及配置或密钥时，先确认是否会触碰 `.env`、证书、第三方 token。

## 3) Skill 使用规范

1. 任务命中 skill 时必须优先用 skill。
2. 同时命中多个 skill 时，按最小必要集使用，避免过度加载。
3. 使用 skill 前先读取其 `SKILL.md`，只加载任务需要的部分内容。
4. 缺少 skill 时，优先用 `skill-installer` 安装后继续开发。
5. 安装失败时立即启用 fallback，不允许因 skill 阻塞交付。
6. 每次执行应明确说明：用了哪个 skill、为何使用。

## 4) 分支与提交流程

1. 日常开发从 `dev` 拉分支：
   - 功能：`feat/*`
   - 修复：`fix/*`
2. 非紧急场景禁止直接在 `main` 开发。
3. commit message 必须符合约定前缀：
   - `feat` `fix` `docs` `style` `refactor` `perf` `test` `chore` `revert`
4. 每个 commit 尽量单一关注点，避免把无关改动混在一起。
5. 下班前必须 push；未完成也要 `WIP` 提交并 push 分支。

## 5) 测试与验证门槛

1. 后端改动至少执行：`npm run test:backend`
2. 小程序改动至少执行：开发者工具基础冒烟
3. 配置或部署改动至少执行：
   - 服务状态检查
   - 关键健康检查接口验证
4. 任何未验证项必须在交付说明里明确标注。

## 6) PR 与发布规则

1. 先合并到 `dev`，通过验证后再发布到 `main`。
2. PR 必须写清：
   - 变更范围
   - 测试结果
   - 回滚方式
3. 发布前确认：
   - 域名/HTTPS/后端服务状态正常
   - 数据库连接可用
   - 健康检查通过

## 7) 安全与密钥规则

1. 严禁提交真实 `.env`、`AppSecret`、PAT、数据库明文口令。
2. 所有密钥只放在运行环境或密钥管理系统。
3. 若密钥曾在对话或日志中暴露，必须尽快轮换。
4. 生产环境禁止 `CORS_ALLOW_ORIGINS=*`。

## 8) 变更完成定义 (Definition of Done)

一项任务只有同时满足以下条件才算完成：

1. 代码实现完成并通过对应验证。
2. 文档同步更新。
3. 分支、commit、PR 流程符合规范。
4. 无敏感信息泄露风险。
5. 交付说明包含“做了什么、如何验证、剩余风险/下一步”。
